# Byte-Sized Brain

**Post-training quantization, measured honestly — 4 model families, 3 modalities, 2 frameworks, 2 runtimes, and one device-agnostic harness that runs on x86 today and ARM64 (emulated or real) with a single command.**

[![CI](https://github.com/vardhjain/Byte-Sized-Brain/actions/workflows/ci.yml/badge.svg)](https://github.com/vardhjain/Byte-Sized-Brain/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)
[![Python 3.10+](https://img.shields.io/badge/python-3.10%2B-blue.svg)](pyproject.toml)

Quantization is the cheapest way to make a model smaller and faster — but *how
much* do you actually gain, and *what does it cost in accuracy*? Byte-Sized Brain
answers that with one reproducible toolkit: it trains four models, quantizes each
with the technique that fits it, and benchmarks size / accuracy / latency / memory
through **one device-agnostic harness** that runs the same on your laptop, in a
container, on emulated ARM, or on real ARM silicon.

**The headline:** post-training quantization shrinks every model by **~69–75%**.
Accuracy is essentially free on the dense net, LSTM and transformer (**≤2%**) —
the static-INT8 **MobileNetV2 is the honest exception** (a ~17 pp drop: depthwise
convolutions are notoriously sensitive to full-integer PTQ). On the transformer,
INT8 also cuts latency by **~40% (1.7×)**. Full numbers + charts:
[docs/report.md](docs/report.md); how it's measured (and its caveats):
[docs/methodology.md](docs/methodology.md).

> Committed results are native **x86**. The identical harness produces **ARM64**
> rows via `make benchmark-arm` (QEMU-emulated) or the cloud recipe in the
> methodology; each row is stamped `arch` / `emulated` so the two never get
> confused.

## The four pipelines

| Pipeline | Model | Data | Modality | Framework → Runtime | Quantization |
|---|---|---|---|---|---|
| `ffn_mnist` | Dense net | MNIST | vision | TensorFlow → TFLite | FP32 → **static INT8** |
| `cnn_cifar10` | MobileNetV2 + head | CIFAR-10 | vision | TensorFlow → TFLite | FP32 → **static INT8** |
| `rnn_imdb` | LSTM | IMDB | sequence | TensorFlow → TFLite | FP32 → **dynamic-range** |
| `distilbert_imdb` | DistilBERT | IMDB | NLP | PyTorch → ONNX Runtime | FP32 → **dynamic INT8** |

## Quickstart

```bash
git clone https://github.com/vardhjain/Byte-Sized-Brain
cd Byte-Sized-Brain
pip install -r requirements.txt        # pinned, reproducible
pip install -e .                       # the `bsb` CLI

bsb list                               # available pipelines
bsb run ffn_mnist                      # train + convert + benchmark
bsb run all --smoke                    # tiny end-to-end run of everything (seconds)
bsb report                             # aggregate CSVs -> docs/report.md + charts
bsb info                               # device, arch, and library versions
```

The lifecycle is four verbs, any pipeline (or `all`):

```bash
bsb train     <pipeline>   # -> artifacts/<pipeline>/fp32_source
bsb convert   <pipeline>   # -> fp32 + quantized artifact
bsb benchmark <pipeline>   # -> benchmarks/results/<pipeline>.csv
```

```
        ┌──────────┐   ┌───────────┐   ┌──────────────────────────┐
 data ─▶│  train   │─▶ │  convert  │─▶ │ benchmark (shared harness)│─▶ CSV ─▶ report
        │ TF / HF  │   │TFLite/ONNX│   │ size·acc·latency·memory   │        (charts +
        └──────────┘   └───────────┘   │ stamped device/arch/emul. │         report.md)
                                        └──────────────────────────┘
```

Prefer Make? `make run-ffn_mnist`, `make test`, `make smoke`, `make report`,
`make benchmark-arm` (see `make help`).

### Docker / ARM64 (the edge story)

```bash
make docker-build                      # x86 image
make docker-build-arm                  # aarch64 image (buildx + QEMU)
make benchmark-arm                     # full smoke benchmark under emulated ARM64
```

Real ARM latency without a Raspberry Pi: run the same commands on a free **Oracle
Ampere A1** or **AWS Graviton** instance — results are stamped `emulated=false`.
Full instructions (and a real-Pi appendix) in [docs/methodology.md](docs/methodology.md).

### Try it: FP32 vs INT8 live

Classify a review through both precisions side by side:

```bash
bsb run distilbert_imdb         # produce the artifacts (once)
bsb demo distilbert_imdb        # built-in example reviews, or pass your own (quoted)
```
```

----------------------------------------------------
fp32          POSITIVE    97.8%    51.51ms  255.55MB
int8          POSITIVE    97.5%    24.83ms   64.27MB
```

Same verdict, **4× smaller and ~2× faster**. There's also a one-screen Streamlit

## How it's measured

One harness measures every variant identically: accuracy, latency
(mean / p50 / p95), and **process-level** RSS delta & peak. Each result row is
self-describing — `device`, `arch`, `os`, `emulated`, and the exact library
versions — so x86, emulated-ARM and real-ARM numbers can be compared honestly and
never silently confused. Determinism via `seed_everything`; representative
datasets for static PTQ are **real samples, never random noise**. Details and
caveats: [docs/methodology.md](docs/methodology.md).

## Reproducibility

- **Pinned environment** in `requirements.txt`; library-style extras
  (`pip install -e ".[tf]"`, `".[torch]"`, `".[all,dev]"`) in `pyproject.toml`.
- **Deterministic** seeds across Python/NumPy/TF/Torch.
- The committed CSVs were produced by the committed code; each carries its own
  `lib_versions`. The committed CNN config is a CPU-feasible frozen-backbone
  baseline (see methodology §5).
